## 需要收口的差距

### G-01｜静态与构建门槛缺少最终记录（收官阻断）

最初任务书要求先做 `gofmt`、Go 测试/构建/vet/race、`npm ci` 与前端检查，并在 E2E 后再次运行 Go 测试/构建/vet/race、前端构建/类型检查/lint 和 `git diff --check`。现行报告没有这些检查的结果表或日志引用。收官前应以**当前代码状态**执行或找到同状态的可信结果，记录命令、退出码、执行时间和证据路径；失败项修复后重跑受影响门槛。

### G-02｜源码到运行镜像的链条没有随报告交付（收官阻断）

本机日志能看到 `--no-cache` 构建、独立标签及 Kind 加载的镜像 ID，但报告只有“重新构建”的叙述。收官证据至少需要：源码提交及工作树状态、构建入口、标签和镜像 ID、Kind 实际运行的控制器与执行器 Pod `imageID`。如 Pod 证据已随测试集群清理而无法恢复，应在下次受控验证中补采，不能由“Kind 已加载镜像”代替“Pod 实际运行该镜像”。

### G-03｜关键断言只有文字，缺机器核对摘要（收官阻断）

创建和销毁的精确审批、创建前无 Apply、更新前后 Service UID、删除后的 NotFound/404 等结论已写进报告，却缺一份按测试运行编号归档的核对摘要。现有销毁终态 JSON 只能直接证明销毁 Apply 的终态，无法单独证明审批对象与执行对象全字段相符。应整理为短小的证据附录：每项只给出对象类型、关键字段相等结果和最终状态；完整 ID 留在附录，不堆入面向人的正文。若原始对象已删除且没有留存，应对无法重建的断言做针对性补测。

### G-04｜审批状态在页面上持续显示 `Pending`（体验缺陷，需明确处置）

报告截图显示创建 Apply 成功、环境 Ready 时，“最新审批”仍为 `Pending`。当前[状态投影](../internal/console/readmodel.go#L385)只有在 `ChangeApproval.status.approvedAt` 或 Ready 条件存在时才显示 `Approved`；仓库中的控制器路径未见对应状态写入。实际执行已被精确审批对象放行，因此这是**页面状态与执行结果不一致**，不是本次 Apply 失败。收官前应修正投影/状态来源并做针对性页面复核；若决定延期，须把它列为明确的已知问题，而非仅用脚注带过。

### G-05｜报告可复现信息不足（文档收口）

报告缺本轮运行编号、测试环境与测试数据的简短索引，也未把原任务书的 13 个门槛映射到证据。草稿宽屏图使用删除后补拍的独立“仅预览”对象，报告已如实注明，但评审者仍需要知道它与实际创建对象分别对应哪一步。保留目前“用例设计 → 方法 → 截图”的人性化正文；增加**一页证据索引与门槛矩阵**即可，不需要把镜像摘要和大段日志塞回正文，也不需要引入新的浏览器测试框架。
